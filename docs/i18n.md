# Internationalization Architecture

## 1. Scope

Bahasa Indonesia (`id-ID`) and English (`en`) are first-class from the first product slice. The organization has a default locale; each user may override it. A document/report may also select an output locale without changing stored business data.

## 2. Separation of meaning and presentation

Store stable locale-neutral codes for roles, statuses, account types, currencies, tax rules, units, and events. Translations are presentation resources. Never persist translated status labels as logic keys or use localized formatted numbers/dates for calculations.

Organization-custom labels are stored by stable key with optional `id-ID` and `en` values. Fallback order is user locale → organization default locale → product default (`id-ID` for the initial market) → stable safe label. Missing translations are observable in non-production and test environments.

## 3. Translation organization

Messages are namespaced by domain and feature, for example `sales.invoice.status.draft`. ICU-style messages handle variables and plurals. Avoid sentence fragments assembled in code. Validation errors, email templates, exports, report headings, accessibility labels, and empty/error states are included in translation coverage.

Accounting/tax terminology uses a professionally reviewed bilingual glossary. Business Mode and Accounting Mode may use different approved labels for the same canonical concept, but identifiers and behavior remain shared.

## 4. Dates, numbers, money, and input

Use `Intl`-compatible formatting with explicit locale, timezone, and currency. Business dates are stored as dates; instants are UTC and displayed in the organization/user timezone. Parsing is stricter than display formatting: input accepts documented Indonesian/English conventions, normalizes to decimal/date values, and asks for clarification when ambiguous.

IDR is the organization-creation default for the initial market, not a platform restriction. Organizations may select other valid ISO 4217 currencies. Currency scale, accounting precision, and display precision are separate centrally configured policies. Never calculate from localized strings.

## 5. OCR and imports

OCR normalization recognizes Indonesian month names, common invoice vocabulary, `Rp`, comma/dot separator patterns, and local date formats, while retaining original text and confidence. Ambiguous amounts/dates are flagged for review. Imports declare locale/format and show a preview before commit.

## 6. Routing and rendering

Locale selection must work with Next.js server rendering without hydration mismatch. URLs may include locale if product research supports it; organization context must never be inferred solely from locale routing. User choice is persisted as a harmless preference and/or server profile, not mixed with auth tokens.

## 7. Quality controls

- Pseudolocalization and missing-key tests.
- Snapshot/visual checks for long Indonesian and English strings.
- Locale matrix tests for parsing and formatting dates, decimals, currency, and negative values.
- Bilingual accessibility and keyboard/screen-reader checks.
- Glossary review by Indonesian accounting/tax professionals before compliance-oriented release.

## 8. Initial terminology requiring review

Confirm consistent translations for journal entry, posting, reversal, trial balance, opening balance, period closing/reopening, receivable/payable, credit note, inventory valuation, weighted-average cost, tax base, withholding, financial position, and SAK EMKM-oriented notes. Product copy must distinguish plain-language Business Mode from formal Accounting Mode without changing meaning.
